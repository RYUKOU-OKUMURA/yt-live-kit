## 2. 発端 — 動画詳細ページの UX 相談

すべての発端は、ユーザーの次の一言だった。

> 各動画の動画詳細ページが全部階層構造になっててUIがわかりにくいしUX的にも体験が悪いんだけど、どうしたらもっと使いやすくなる？

これを受けてコードを確認したところ、次の構造上の問題が判明した。

- 階層の深さが最大 4〜5 段（ページ → 番号付き subheader → expander → expander または markdown 見出しによる階層偽装 → container → dialog）
- Streamlit は `expander` を入れ子にできないため、[`src/yt_live_kit/ui/views/shorts.py`](../src/yt_live_kit/ui/views/shorts.py) の「ショートをまとめて生成」は `### ` markdown 見出しで階層を偽装していた
- 進行モデルが 2 つ並存していた（5 段ステッパー vs 番号付き見出し 1〜7）
- `expander` が「状態の隠蔽装置」になっていた（閉じていると中に成果物があるか画面から分からない）
- ショート機能が「単発生成」「長い候補を刻む」「まとめて生成」の 3 つに分裂し、同じ `expander` の中に入れ子になっていた

## 3. チャプター表示の扱い

ユーザーから次の指摘があった。

> ぶっちゃけさ、チャプターはほぼ確認せずにそのまま概要欄に反映させちゃうから、このページに表示しなくてもいいんじゃね？それか最下部でもいいような気がする。

検討の結果、「削除」でも「最下部へ移動」でもなく、「概要欄反映の入力データ」として統合する結論に至った。理由は次の 3 点である。

1. 概要欄反映のダイアログは既に更新前後の全文を見せており、チャプター本文をページ上にも常時表示するのは二重表示になる
2. チャプター生成と概要欄反映は、ユーザーの認識としては実質 1 つの仕事である
3. 最下部へ移動するだけでは、チャプターと概要欄反映というセクションが 2 つ残る点は変わらない

ただし「タイムラインをコピー」機能は、OAuth 未設定時の手貼りフォールバックとして残すことを決めた。

## 4. Codex 監査との突き合わせ（v3.1 の成立）

ユーザーが独自に Codex CLI へ同じ調査を依頼し、その結果を提示した。

> codexの調査と推奨修正はこれらしい。君の上記の意見と照らし合わせて、どの修正がおすすめかな？

このとき提示されたのが [.codex/audits/video-detail-ux/audit.md](../.codex/audits/video-detail-ux/audit.md) である。独立に行った 2 つの分析（Codex の監査と、コードレビューによる分析）が同じ結論に到達したことは記録に値する。両者が一致した点は次の 3 つ。

- 縦積みと入れ子の廃止（1 画面全部見せから「実際に行う仕事を選んで進める」構成へ）
- チャプターの概要欄への統合（本文は非表示、状態だけ表示）
- 量産（キュー量産）フローの主導線化

一方で、Codex 案の方が優れていた点も 2 つあった。

1. **単発生成の格下げ。** [`src/yt_live_kit/ui/components/upload.py`](../src/yt_live_kit/ui/components/upload.py) は量産 manifest しか読まないため、単発生成したショートは予約投稿へ進めないという罠がある。この制約を「生成ファイル」（`shorts/output` の全 mp4）と「予約可能」（検証済み量産 manifest の成功 item）という別指標で可視化する提案
2. ワークスペース外に常時表示する状態カード

ユーザーはこの統合方針を明確に承認した。

> 両者の案を鑑みての判断ならそれでOKだよ。正確に確実に実装に入れるようにドキュメントを整理または新規作成して。

これを受けてコミット `69697e1`（v3.1）が作成され、FR-17 の改訂、FR-31・FR-32 の新設、AC-31〜AC-33 の追加、U6・U7・U8 の新設が行われた。

## 5. 寄り道 — 外部 API で品質は上がるか

ここで一度、生産ラインとは直接関係のない質問が挟まった。

> あとさ、ChatGPTとかDeepSeekとかのAPI使ったらショート動画とかハイライト動画のクオリティーって上がる？

回答の要点は「ほぼ上がらない」というものだった。理由は次のとおり。

- Codex CLI は既に GPT-5 系モデルを使っており、他の LLM API へ乗り換えても変わるのは課金形態だけである
- 品質の上限を決めているのは (1) YouTube 自動字幕の精度（FR-22 自身が「自動字幕の品質が上限を決めるため、確認ステップは省略しない」と明記している）、(2) 区間選定がテキストのみで音声・映像を見ていないこと、(3) ffmpeg の仕上がりであり、いずれも LLM の交換では動かない
- NFR-11「従量課金 API を使わない」にも抵触する

効果があるとすればローカル Whisper の導入・`prompts/` の改善・音声エネルギー解析の順である、という優先順位も併せて共有した。

ユーザーの判断は次のとおりだった。

> なろほど。じゃあとりあえず今回のv3.1の実装を完了させてから考えようか。

## 6. 実機確認で分かったこと

S6（切り抜き候補からのショート用サブ区間提案）の実装後、実際に生成された成果物を検証した。対象は `data/LB4px1wRFnY/shorts/` である。

| 確認項目 | 結果 |
|---|---|
| サブ区間提案 | `data/LB4px1wRFnY/shorts/cutplan/cut_clip_002.json` に 3 区間（28 + 10 + 19 秒） |
| 出力解像度 | 1080x1920 |
| 出力尺 | 57.04 秒（採用区間合計 57 秒と一致、10〜180 秒内） |
| 字幕の累積オフセット | ASS が 0:00:00.00 → 0:00:57.00 で尺と完全一致（S3 の最大リスクだったズレなし） |
| 字幕焼き込み | ffmpeg-full + subtitles フィルタで returncode 0（S7 の修正も実証） |
| atomic replace | 一時ファイル経由で正式出力へ置換 |
| 中間物クリーンアップ | segments ディレクトリが空 |

この結果を受けたユーザーの実機フィードバックは次のとおりだった。

> 繋ぎ目のフリーズは無さそうだね。ただやっぱり字幕の精度が低いね。テロップの切り方とか、「Claude」「Codex」に誤植があって目立つね。

原因を調査したところ、`data/LB4px1wRFnY/shorts/` には telop ディレクトリが存在せず、Codex 台本を通さず YouTube 自動字幕（VTT）を直接焼き込んでいたことが判明した（実際に `data/LB4px1wRFnY/shorts/telop` は存在しないことを確認済み）。誤植は YouTube 側の音声認識由来である（例: 「クロード」が次行で「フロード」、「感覚すけど」）。

これは FR-30 のスコープ記述「テロップ台本（FR-22）の生成・確認は本導線では行わず、既存のキュー量産（FR-26）に委ねる」どおりの**仕様上の帰結であり、バグではない**。

続けて、ユーザーからスクリーンショット付きで次のフィードバックがあった。

> 切り抜き候補からのショートを作成が機能してないね。多分。
> 長い候補を刻んでショートにするは機能する。
> けど、区画を提案されて開始時間と終了時間を提案されたところで、実際の話してる内容がわからないから自分で調整できない。実際に今試しに作ってみたけど、重要な部分が最後に切れてたから投稿には採用できないね。
> あと、生成した動画のプレビューが大きすぎて確認がしにくい。

これを受けて全数調査を行い、次の実測値が出た。この数字は v3.2 の設計判断の根拠になった。

- 切り抜き候補は全 47 動画で **142 本、うち 180 秒以下は 0 本（0%）**
- ハイライト候補は **0 本**（1 動画も生成されていない）
- 帰結: 切り抜き候補からの単発生成もキュー量産も 180 秒上限で弾かれ、実データでは「刻む」（FR-30 / S6）が唯一の入口になっている
- [`src/yt_live_kit/ui/components/short_cut.py`](../src/yt_live_kit/ui/components/short_cut.py) の `_render_plan()` は id / title / 秒数 / 開始・終了入力 / reason しか表示せず、区間の文字起こしが無い。FR-30 は「人の確認を必須とする」と定めているが、確認材料が画面に無かった
- `st.video` の幅未指定が 4 箇所（[`ui/components/short_cut.py`](../src/yt_live_kit/ui/components/short_cut.py) / [`ui/views/shorts.py`](../src/yt_live_kit/ui/views/shorts.py) / [`ui/components/shorts_queue.py`](../src/yt_live_kit/ui/components/shorts_queue.py) / [`ui/views/highlights.py`](../src/yt_live_kit/ui/views/highlights.py)）

## 7. 転換点 — 「量産」という言葉のズレ

このセクションが本ドキュメントの核心である。ユーザーの発言を原文のまま引用する。

> そもそもさ、「量産」って言葉に引っ張られすぎてない？多分「一度に大量の動画を生産できる」って認識じゃない？だから余計な機能を実装して詰まってたり、UIがごちゃごちゃしてるんだと思う。
> 俺としては「毎日3本確実に安定して生産する」ことが目的だから、それなりにクオリティーは担保したいのよ。
> そもそも今までショート動画を作ってこなかったから、それが1日3本、しかも過去のライブ配信を素材にできるなんてめっちゃ最高じゃんって感じ。
> 多分イメージが食い違ってる。

これは v3 設計そのものの前提を揺るがす指摘だった。認識のズレを整理すると次のようになる。

| | v3 の設計が向いていた先 | 実際の目的 |
|---|---|---|
| 価値 | 一度に大量生成できること（ボリューム） | 毎日 3 本を確実に出し続けること（ケイデンス × 品質） |
| 1 本の扱い | N 本まとめて確定して一括ジョブ | 1 本ずつ中身を確認して仕上げる |
| ボトルネック | エンコードの手間 | 人が品質を確認する工程 |

v3 の目的文はもともと「ショート動画の安定量産」だった。この言葉から、S4 は「複数選択 → 全確定 → 一括ジョブ → manifest → softfail」というバッチ機構へと育っていった。つまり「量産」という言葉そのものが設計の方向を引っ張っていた、という経緯である。

この会話で初めて判明した設計上の欠落もあった。FR-28 の予約ポリシーが `daily_time` 単一値であり、**1 日 1 枠が前提**になっていた。毎日 3 本という目的に対応していなかった。

## 8. 「生産ライン」の言語化

続けてユーザーは、望んでいる仕組みをこう言語化した。

> 時間は決めてない。
> あとこれはハイライト動画生産でも言えることだけど、「安定してクオリティーがブレない確実な生産」ができる機構と流れとUIが欲しいんだよね。言いたいことわかる？

ここで言語化されたのは、欲しいのは「機能の寄せ集め」ではなく「生産ライン」だということである。現状の UI は「できること」が並んでいるだけで、どの順に何を確認すれば 1 本が完成するかを毎回自分で組み立てる必要があり、それゆえに品質がブレていた。

工程モデルとして次の流れを整理した。

```
素材を選ぶ
  → 区間を決める 〔ゲート①: 中身を見て OK〕
    → 文言を整える 〔ゲート②: テロップを見て OK〕
      → 生成
        → 最終確認 〔ゲート③: プレビューを見て OK〕
          → 予約 / 完成
```

各ゲートを通過するまで次に進めない、という設計である。

このモデルから 3 つの原則を導いた。

1. **品質は「人の注意力」ではなく「工程」が保証する。** S4 の「全台本を確定するまでジョブが始まらない」という設計はこの思想として正しかったが、門をバッチ単位に置いたのが誤りで、門は 1 本ごとに置くべきだった
2. **行き止まりゼロ。** ラインに乗せた素材は必ず「予約済み / 完成」まで到達できること
3. **毎回選ばせない。** レイアウト・テロッププリセットを毎回選ばせるのは摩擦であると同時にブレの発生源になる

「毎日 3 本」とは、このラインを 1 日 3 周まわすことである。ハイライト動画も同じ型で、ゲート②（テロップ確認）が無い短いラインとして扱える。

## 9. 優先順位の確定

ユーザーはこの理解を確認したうえで、優先順位を明確にした。

> 合ってる。イメージは合ってる。
> さらに言うと、俺の中の最優先は「ショート動画の生産フローの確立」なんだよね。横向きのハイライト動画はおまけというか、この生産ラインがあれば派生で生産するのはそんなに難しくないって認識。
> で、今となっては概要欄へのチャプター入れはおまけのおまけ。もう実装して機能してるしね。
> ここは、今後のライブ配信後にチャプターが漏れなく入れられれば問題なし。

確定した優先順位は次のとおり。

| 優先度 | 内容 |
|---|---|
| ① 最優先 | ショート生産ラインの確立 |
| ② 派生 | 横型ハイライト動画（生産ラインができれば低コストで実現できる） |
| ③ 保守のみ | 概要欄チャプター反映（実装済み・機能済み。再設計しない） |

この優先順位は計画に直接反映された。U7（概要欄反映の fingerprint 化）は v4 候補へ保留され、FR-21 の fingerprint 化段落も保留扱いになった。

## 11. 未決の論点（このドキュメント作成時点）

このドキュメントを作成する直前、ユーザーから次の指摘があった。

> 方向性の解像度が上がったから、UIも変わるよな。

この指摘が示す論点は次のとおりである。v3.1 で決めた「3 ワークスペース（素材候補 / ショート作成 / 公開・投稿）」は「どの作業をするか横に選ぶ」モデルであり、生産ラインの「どの工程まで進んだか縦に進む」モデルとは噛み合わない。素材候補は工程①、公開・投稿の予約部分は工程⑥にあたり、これらをワークスペースとして横並びに分けると、ラインが分断されてしまう。

方針として次が挙がっているが、**未コミットであり、要件書・実行計画書の改訂が必要**な状態である。

- 3 つ並列のワークスペースではなく、「1 本のライン + 補助（ハイライト / 概要欄 / 詳細・再生成）」という構成へ変える案
- あわせて「今日の枠 n/3」をステータスバーに常時表示する案
- 「今日の 3 枠」を起点にした専用ページは作らない（ラインが回り始めてから v4 で判断する）

この改訂が行われる場合、AC-31 の「3 つのうち選択中の 1 つだけを描画」「作業切り替えだけがワークスペース移動を担う」等の項目は書き直し対象になる。本ドキュメント作成時点では、この論点はまだ requirements-v3.md / execution-plan-v3.md に反映されていない。
