# User decisions and working preferences

## 2026-08-03 — 次期改善の優先順位

- 現行の承認済みスコープは完成扱いとする。
- 次の改善では、装飾的な UI ブラッシュアップより字幕品質を優先する。ただし、生産を止める具体的な UI 問題が見つかった場合は局所修正を先行してよい。
- Whisper は全面導入や全動画の再文字起こしから始めない。まず現行の Codex 補正フローを 3〜5 本で運用し、誤字数・手修正時間・総リードタイムを測る。
- 次に `whisper.cpp` をショート採用区間だけへ適用する小規模スパイクを行い、YouTube 字幕版との精度、処理時間、手修正時間を比較する。
- S9 の正式導入判断では、字幕精度だけでなく動画生産フローの待ち時間とスループットへの影響を重視する。改善効果が追加待ち時間を上回る場合に採用する。

## 2026-08-03 — Whisper の用途と将来の入力媒体

- Whisper はテロップ補正だけでなく、切り抜き候補区間の判断にも利用し、候補抽出の精度向上が確認できるなら採用する方向で検討する。
- 将来はライブ配信以外の動画から切り抜きショートを作る用途も視野に入れる。
- 今後の設計では、特定の配信媒体や既存字幕の有無に依存せず、異なる動画ソースを扱える構造を重視する。

## 2026-08-03 — ショート投稿時の概要欄

- ショート動画の投稿時には、概要欄へチャンネル登録案内と切り抜き元動画の案内が確実に含まれることを重視する。
- 投稿機能や概要欄テンプレートを確認・変更するときは、この 2 種類の案内が欠けないことを明示的に確認する。

## 2026-08-03 — ショートのタイトル・概要欄運用

- 参照した YouTube Shorts のリサーチを、今後のタイトル付けと概要欄運用に活かせるか確認したい意向がある。
- 切り抜き元への導線は概要欄の URL だけでなく、YouTube ネイティブの「関連動画」も重視する可能性がある。今後の仕様検討では、関連動画の設定可否や運用方法も確認対象に含める。

## 2026-08-03 — 改善作業の並行実施

- 別タスクで S9 が進行中でも、変更競合を避けられるなら、タイトル・概要欄・関連動画の改善を同時並行で進めたい意向がある。
- 並行着手を判断する前に、変更対象の安全な分割とマージ順を確認し、競合や手戻りのリスクを把握できることを重視する。

## 2026-08-03 — S9 人手監査の評価基準

- 監査パケットの 4 本について、表示された Provisional gold transcript は「4 本とも文字起こしは概ね問題なし」と評価された。これは運用上参照できる字幕内容としての承認であり、逐字、句読点、固有名詞ごとの表記、cue のミリ秒単位まで完全一致したという意味には拡張しない。
- 字幕内容の承認と編集境界の品質は別に扱う。case 1 はほぼ問題なし。case 2 と 3 は冒頭約 6 秒まで意味のある発話がなく開始境界が不適切。case 4 は開始直後に発話がある一方、約 2〜26 秒がほぼ無発話でショートとして致命的と評価された。
- 人手監査では堅いテンプレートへの再入力を求めず、ユーザーの自然文による所見をエージェント側で構造化する運用を続ける。
- 親候補の音声は保持し、最終 cutplan で冒頭の無発話と長い内部無発話を除去したうえで再確認する設計を重視する。
- 実装時は P6 完了時点の `main` HEAD `f9510d1` を基準とし、S9-4 でも P6 のテロップ契約を維持する。

## 2026-08-04 — S9 の目的と確定フロー

- 目的からの逸脱や細部への過集中を強く避ける。次回以降も P0・P1 と目的達成を先に置き、実用上不要な理想化は抑える。
- 親候補の探索には YouTube VTT を使い、ユーザーが明示選択した区間だけを local Whisper で処理する。全編 Whisper は行わない。
- 選択区間から作る単一の `TranscriptArtifact` を cutplan、telop、queue、line まで一貫して再利用し、人が境界と無音を最終確認する。
- 実動画では case 1 は追加処置なし、case 2 と 3 は冒頭無音を trim して再確認、case 4 は長い内部無発話を gap removal して再確認する。
- S9-5 は `main` へ統合済みとして扱う。

## 2026-08-04 — 実機障害の修正運用

- Whisper 高精度字幕とテロップ生成が実機で失敗した場合、原因説明だけで終わらせず、修正内容を詳細なタスクへ分解して完遂することを重視する。
- 各修正タスクは専用 worktree セッションで実行し、完了報告後に独立レビューを行う。問題がなければ `main` へのマージとコミットまで一貫して進める。
- 設定済みの `ffmpeg-full` が後続処理へ伝播しない問題を修正し、失敗通知と復旧 UI も改善する。
- Codex の自動再試行では呼び出し回数を増やさず、fail closed を維持する。
